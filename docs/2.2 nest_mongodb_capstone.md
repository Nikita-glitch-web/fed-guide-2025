# NestJS + MongoDB Backend — Capstone Requirements (Detailed MongoDB Focus)

This document mirrors the Angular capstone but for the **backend service** built with **NestJS** and **MongoDB**. It specifies the functional scope, endpoints, data model, and deep MongoDB requirements (indexes, aggregations, pagination, transactions, and performance).

> **Tech stack**
- **NestJS** (v10+), **TypeScript**
- **MongoDB** (6.0+) with **Mongoose** (`@nestjs/mongoose`)
- **Yarn** as package manager
- **Jest** + **Supertest** for tests
- **Docker** + `docker-compose` for local DB
- Optional: **Mongo Express** for visual admin

---

## 1) Environment & Project Setup

**Tasks**
- Create a NestJS project: `nest new api` (choose **Yarn**).
- Install Mongo stack: `@nestjs/mongoose mongoose`, types `@types/mongoose`.
- Add `docker-compose.yml` with services:
  - `mongodb` (expose 27017, named volume)
  - `mongo-express` (optional) on 8081 protected by basic auth
- Provide `.env` with: `MONGODB_URI`, `JWT_SECRET`, `PORT`.

**Acceptance Criteria**
- `yarn start:dev` runs API, connects to MongoDB from docker-compose.
- Health endpoint `/health` returns `200` with app and db status.

**Similar Examples**
- Nest Mongoose starter: https://docs.nestjs.com/techniques/mongodb

## 2) Domain & Data Model

Domain mimics the Angular capstone: **Auth + Products**.

### 2.1 Users
- `User` fields:
  - `_id: ObjectId`
  - `username: string` (unique, 3–50)
  - `email: string` (unique, normalized lowercase)
  - `passwordHash: string`
  - `roles: string[]` (e.g., `['user']`, `['admin']`)
  - `createdAt: Date`, `updatedAt: Date`
  - `lastLoginAt?: Date`
- **Indexes**:
  - Unique on `username`
  - Unique on `email`
  - TTL (optional) on a `verificationTokenExpiresAt` if email verification added
- **Validation**: class-validator DTOs + Mongoose schema constraints.

### 2.2 Products
- `Product` fields:
  - `_id: ObjectId`
  - `title: string` (3–80, required)
  - `description?: string`
  - `price: number` (>=0)
  - `rating: number` (0–5, default 0)
  - `stock: number` (>=0, integer)
  - `category: string` (required, indexed)
  - `images: string[]` (default [])
  - `createdBy: ObjectId` (ref User)
  - `createdAt: Date`, `updatedAt: Date`
- **Indexes**:
  - Compound: `{ category: 1, price: 1 }` for filtered sorts
  - Text index: `{ title: 'text', description: 'text' }` for search
  - Optional: partial index for “active” documents if you add `isActive: boolean`
- **Validation**: DTO + Mongoose schema-level rules.

**Acceptance Criteria**
- Mongoose schemas with timestamps and versioning (versionKey enabled or disabled with custom optimistic strategy).
- Necessary indexes are created via schema options or `syncIndexes()` bootstrap.

## 3) Authentication & Authorization

**Tasks**
- Local login with username/email + password (bcrypt/argon2).
- Generate JWT access token (15m) + optional refresh token (7d).
- Guarded routes for `/products/**` (role: `user` or `admin`).
- Role-based decorator `@Roles('admin')` for create/update/delete.

**Acceptance Criteria**
- `POST /auth/login` returns `{accessToken, user}`.
- Protected routes require `Authorization: Bearer <token>`.
- Passwords are never logged; strong hash parameters are used.

## 4) REST Endpoints (Products)

Base path: `/v1/products`

- `GET /` — list with pagination, filters, sort
  - **Query**: `page`, `limit`, `q` (text), `category`, `minPrice`, `maxPrice`, `sort` (e.g., `price:asc`, `createdAt:desc`)
  - **Mongo**: server-side pagination with `limit` + `skip` **or** cursor-based `_id` pagination
  - **Projection**: exclude heavy fields if added later
- `GET /:id` — get by id
- `POST /` — create (auth required, role `user|admin`)
- `PUT /:id` — full update (role `admin` or resource owner)
- `PATCH /:id` — partial update (same rules)
- `DELETE /:id` — soft delete (optional) or hard delete (admin only)

**Acceptance Criteria**
- DTO validation for all inputs (class-validator).
- Error responses return standardized JSON `{statusCode, message, error}`.
- CRUD operations return updated doc snapshots.
- For list: total count + items (or use cursor token).

## 5) MongoDB Specifics (Deep Dive)

### 5.1 Pagination Strategies
- **Offset pagination**: `limit` + `skip`, easy but slower on deep pages.
- **Cursor pagination**: use `_id` or compound field (e.g., `{createdAt, _id}`) with `$lt/$gt` filters.
- Implement **one**; document the trade-offs in README.

### 5.2 Text Search
- Create a **text index** on `title` and `description`.
- Query with `$text: {$search: q}` and project `score: {$meta: 'textScore'}`; sort by `score` then `createdAt`.
- Alternative: regex on `title` (case-insensitive) for prefix search (slower, no index use).

### 5.3 Filtering & Sorting
- Convert query params into a Mongo filter safely:
  - `category` exact match (indexed).
  - `price` range via `$gte`, `$lte`.
  - Prevent injection: whitelist sortable fields; parse `sort` value strictly.
- Prefer sorting by indexed fields; avoid collection scans.

### 5.4 Projections & Lean
- Use **projections** to avoid overfetching.
- Use `.lean()` for read endpoints to return plain objects (faster, no Mongoose hydration) when no hooks/methods needed.

### 5.5 Updates & Atomicity
- Use atomic operators: `$set`, `$inc`, `$addToSet`, `$pull`.
- For array updates, use **`arrayFilters`** for precise mutations.
- Implement **optimistic concurrency**:
  - Option A: default `__v` versionKey and `overwrite: false` updates.
  - Option B: conditional updates with `{ updatedAt: prevValue }` (compare-and-set).

### 5.6 Indexing Plan
- Ensure unique indexes for user identity fields.
- Category + price compound index for product lists.
- Text index on title+description.
- Background index builds for production; track with `currentOp()` if needed.
- Document index selection with `explain('executionStats')` samples in dev.

### 5.7 Aggregations
- Provide aggregation for analytics endpoint:
  - `/v1/products/analytics/summary`:
    - total products
    - avg price, min/max price
    - count by category (top 10)
- Pipeline example (conceptually): `$match` (filters) → `$group` → `$sort` → `$limit`.
- Use `$facet` to return both list and counts in one round-trip (optional).

### 5.8 Transactions (Optional, Advanced)
- Convert to replica set in local docker to enable multi-document transactions.
- Use `withTransaction` for a scenario (e.g., decrement stock + create audit log).
- Set write concern `{ w: 'majority' }` for transactional ops; be ready to retry on transient errors.

### 5.9 Read/Write Concerns & Consistency
- Default read preference `primary` for consistency.
- If replicas used, read preference can be tuned (e.g., `primaryPreferred`).
- Validate write concern in env; avoid `w: 0` in production.

### 5.10 TTL & Archival (Optional)
- If soft delete or temporary documents are added, use TTL index on a `expiresAt` field.
- For archival, move documents to a separate collection via batch job (cron/queue).

## 6) Performance & Observability

**Performance**
- Use `.lean()` on reads, avoid unbounded `.find()`.
- Avoid `$regex` without anchors or indexes.
- Paginate every list endpoint; default `limit` ≤ 50.
- Cache hot reads at service layer (optional Redis).

**Observability**
- Logging: pino/winston JSON with correlation id.
- Metrics (optional): expose Prometheus metrics.
- Error handling: global filter to normalize errors.

**Acceptance Criteria**
- Product list endpoint returns < 200ms locally on a warmed DB (10k docs seeded).

## Appendix D — Aggregation (Conceptual)

```js
db.products.aggregate([
  { $match: { /* filters from query */ } },
  { $group: {
      _id: '$category',
      count: { $sum: 1 },
      avgPrice: { $avg: '$price' },
      minPrice: { $min: '$price' },
      maxPrice: { $max: '$price' }
  }},
  { $sort: { count: -1 } },
  { $limit: 10 }
]);
```

## Appendix E — Cursor Pagination (Conceptual)

- Sort by `{ createdAt: -1, _id: -1 }`.
- Client sends `cursor=<lastCreatedAt>_<lastId>`.
- Next page filter: `{ $or: [ { createdAt: { $lt: lastCreatedAt } }, { createdAt: lastCreatedAt, _id: { $lt: lastId } } ] }`.
- Encode/decode cursor safely (base64 with HMAC if needed).
